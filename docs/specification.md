# CWM MinIO Tierer Specification

## Status

This document is authoritative. `TODO.md` is the original concept and is not
an implementation contract.

## Goal

Provide two Go executables:

- `redis-updater` accepts object-access records and stores hourly counters in
  standalone Redis.
- `minio-tierer` scans current logical objects, marks low-usage objects for an
  externally configured MinIO lifecycle transition, and temporarily restores
  high-usage transitioned objects.

The exact integration-tested MinIO release is
`RELEASE.2025-07-23T15-54-02Z`. Other releases are not rejected at runtime but
are unsupported until tested.

## External Contracts

- Vector receives and filters MinIO audit events. Filtering, durable MinIO to
  Vector handoff, and durable Vector delivery are outside this project.
- Vector MUST exclude traffic generated by the tierer's MinIO credentials.
- Every valid record received by `redis-updater` counts as one access. The
  updater does not interpret the originating MinIO operation.
- MinIO lifecycle rules, tier targets, and marker-rule matching are externally
  provisioned. The tierer neither creates nor validates lifecycle rules.
- Updater authentication and TLS termination are supplied by a trusted network
  boundary. The service MUST enforce resource limits and safe HTTP timeouts.
- Exactly one tierer replica may run. Leader election is outside scope.
- System clocks MUST be synchronized. The updater uses its UTC arrival time,
  not an event timestamp.

## Redis Schema

Redis v1 support is standalone only. All keys use a required stable instance
ID and the `cwm-minio-tierer:v1` namespace. Bucket and object components are
base64url encoded without padding.

```text
cwm-minio-tierer:v1:<instance>:access:<YYYY>:<MM>:<DD>:<HH>:<bucket>:<object>
cwm-minio-tierer:v1:<instance>:cursor:<scope-hash>
cwm-minio-tierer:v1:<instance>:budget:<YYYY>:<MM>:<DD>:<kind>
```

Coverage records are external and enabled by default. When enabled, they use a
required configurable Go time-format template plus exact expected value. The
template MUST vary by UTC hour and SHOULD include the instance ID and external
filter/schema generation. When coverage is disabled, low-window coverage is
treated as complete and no coverage keys are read.

Counters use absolute expiry derived from the end of their UTC hour. Counter
retention is configurable and MUST exceed `max(B,D)+1h`. Missing access keys
equal zero only when coverage is disabled or all required low-window coverage
records match. Wrong types, negative values, malformed integers, and overflow
are errors.

Redis MUST be configured with persistence and `noeviction` for apply mode.
Lossy Redis recovery invalidates coverage externally. Redis durability beyond
an acknowledged command is an operational responsibility.

## Updater HTTP API

- Endpoint: `POST /`.
- `application/json` accepts exactly one object.
- `application/x-ndjson` accepts one or more newline-delimited objects.
- Each object has exactly two non-empty string fields: `bucket` and `object`.
- Unknown fields, duplicate fields, trailing JSON, blank NDJSON records,
  malformed UTF-8, empty bodies, and unsupported media types are rejected.
- The entire bounded request is validated before enqueueing.
- All records in one request use the UTC hour captured when the request is
  accepted.
- One request is never split across internal Redis batches.
- Duplicate keys are aggregated before Redis execution.
- Internal batching is bounded by event count, unique key count, queue size,
  body size, and maximum wait.
- Each internal batch uses one prevalidated Lua script. The script validates
  all existing key types and integer bounds before its first write, then
  performs all `INCRBY` and `EXPIREAT` operations without interleaving.
- The handler responds only after Redis acknowledges the containing batch.
- Both application Redis clients MUST disable transparent command retries.
  Non-idempotent counter and budget scripts receive one client attempt so an
  ambiguous transport reply reaches Vector or scanner-level handling. A
  deterministic `NOSCRIPT` reply MAY reload and execute the script once.
- Ambiguous Redis results return the configured failure status. Vector retries
  may overcount; exactly-once counting and event IDs are out of scope.

Success and failure statuses default to `200` and `500`. A non-5xx failure
status requires `UPDATER_ACCEPT_DATA_LOSS=true`. A non-2xx success status
requires `UPDATER_ACCEPT_DUPLICATE_RISK=true`. Both overrides MUST emit a
persistent metric and startup warning.

## Time Windows

Let `H` be an evaluation time truncated to a UTC hour.

- Low usage is `sum([H-B, H)) < A`.
- Low windows contain completed hours only.
- Every low-window hour MUST have the configured complete coverage value.
- Low eligibility requires `LastModified <= H-B`.
- High usage with current hour excluded is `sum([H-D, H)) > C`.
- High usage with current hour included is the current hour plus the preceding
  `D-1` hours, with `sum > C`.
- Current-hour inclusion for high usage is configurable and defaults false.
- High decisions do not require coverage records.

`A`, `B`, `C`, `D`, and `E` are required positive environment configuration in
apply mode. `A` and `C` are non-negative integer thresholds; `B` and `D` are
positive hours; `E` is a positive MinIO restore-day value.

## Object Identity And Tagging

Usage identity is the logical current `bucket/object` key, including versioned
buckets. Historical versions are not scanned. Before tagging, the tierer
re-stats the candidate and skips if ETag, LastModified, size, or available
VersionID differs from the listed object.

The marker key and value are required configuration. The key is exclusively
reserved for this application:

- Matching marker: no-op.
- Conflicting marker value: replace the reserved value.
- Fewer than ten unrelated tags: preserve them and add the marker.
- Ten unrelated tags: skip and report.

Tag updates are read-merge-write and cannot be made compare-and-swap atomic.
The tierer verifies the result but accepts the residual concurrent tag race.

## Transition And Restore State

The marker requests transition through external lifecycle configuration. A
marker is not evidence of transition. MinIO transition/restore metadata is the
sole authority for restore eligibility.

- Local low-qualified object: reserve budget and add marker.
- Marker present but local: pending external lifecycle; do not restore.
- Transitioned and high-qualified: request restore for `E` days.
- Restore ongoing: treat `RestoreAlreadyInProgress` as pending.
- Active completed restore and high-qualified: extend on every qualifying full
  scan.
- Active completed restore and not high-qualified: do not extend.
- Expired restore and high-qualified: request restore again.
- Transitioned object without marker: remains restore eligible.

Initial restore charges one restore attempt and the listed object size. Expiry
extension charges one restore attempt and zero bytes. Restore duration follows
MinIO calendar-day/UTC-midnight semantics, not exactly `E*24h`.

## Scanner, Cursor, And Scope

- Process all visible buckets except configurable exact-name and prefix
  exclusions.
- Skip zero-byte directory objects ending in `/`.
- Use sorted current-object listing and persist the last fully handled
  `(bucket, object)` cursor in Redis.
- Cursor state includes the instance and a scan-scope/configuration hash.
- Use one evaluation hour per bounded work chunk.
- Persist the cursor after a completed chunk, never before its outcomes.
- Listing, Redis count, coverage, budget, and cursor errors stop the scan
  without advancing the affected chunk.
- Isolated tag/restore errors are reported and advanced; they retry next full
  traversal.
- At inventory completion, reset the cursor durably, then wait the configured
  completion delay.
- Cursor age MUST be computed continuously from the persisted cursor's
  `UpdatedAt`, initialized when that cursor is loaded for resume, clamped to zero
  for future timestamps, and reset to zero only after successful durable cursor
  removal at full traversal completion.
- Scans never overlap. There is no object-count, scan-duration, or restore
  latency guarantee.

## Audit Mode And Budgets

Audit mode is the default and performs no MinIO mutation or budget reservation.
Apply-mode budgets are unlimited when unset or empty. When set, they MUST be
positive UTC daily limits for:

- transition attempts;
- transition bytes;
- restore attempts, including renewals;
- initial restore bytes.

The tierer atomically checks and reserves count and bytes in Redis before a
MinIO mutation when at least one limit for that budget kind is set. Reservations
are never refunded after failures, ambiguous results, or crashes. Budgets limit
attempts, not confirmed outcomes.

## Observability And Operations

Both processes provide structured logs, `/livez`, `/readyz`, and Prometheus
`/metrics`. Metrics MUST avoid bucket/object labels. Required signals include
HTTP records and rejections, queue depth, batch size/latency/errors, risk
overrides, Redis failures, scan progress and duration, coverage skips, cursor
age/errors, budget use/exhaustion, marker outcomes, transitioned state,
restore starts/renewals/errors, and last successful operation times.

## Accepted Risks

The following are consciously accepted and MUST remain documented in README
and operator guidance:

- Arrival-time attribution smears delayed events into later hours.
- At-least-once retries may overcount and trigger retention or extra restores.
- External coverage truth cannot be verified by this application.
- Non-retryable failure overrides can lose events and invalidate coverage if
  the external producer does not account for them.
- Non-2xx success overrides can cause repeated retries and severe overcounting.
- Lua scripts provide isolation, not rollback after arbitrary runtime/resource
  failures; prevalidation only controls deterministic failures.
- Redis is standalone and application availability follows Redis availability.
- Redis persistence and recovery correctness are external responsibilities.
- Lifecycle configuration is external and unvalidated; marking does not
  guarantee transition.
- Logical-current accounting mixes object generations and cannot eliminate
  overwrite/delete-marker races.
- Concurrent unrelated tag writers can lose updates during read-merge-write.
- One tierer replica is an external deployment invariant with no in-app lock.
- Sorted traversal is not a point-in-time snapshot; insertions behind the
  cursor wait for the next traversal.
- Every-scan restore renewal intentionally creates metadata-write amplification
  and can consume restore-attempt budgets before later objects are reached.
- Authentication and TLS are external; incorrect network exposure permits
  forged usage events.
- No scale or action-latency service-level objective is provided.

## Packaging And Validation

The repository supplies both binaries, a non-root multi-stage image, and a
Docker Compose integration environment with standalone persistent Redis and
the exact MinIO release. Kubernetes packaging is out of scope.

Required validation includes unit tests, race tests, vet, binary builds,
container build, Redis integration tests, and pinned MinIO transition/restore
integration tests.
